Exercise 06: The SVG Asset Manifest (Text-Based)

Description

Unlike pixelated raster textures (PNG/JPG), 2D vector graphics engines treat visual entities as scalable structural paths described via text XML string formats (.svg files). Before attempting to bake assets into production packages, an engine needs to model what a vector asset looks like in system memory.

Building directly upon your serialization work from Exercise 0.5, you will create a text-based SVG Asset Manifest Manager. This layer reads actual text SVG data from your disk, stores it inside an structured enum along with its rendering canvas size parameters, and saves the registry out as a human-readable JSON manifest.

Requirements

  2. Define an Asset data enum containing a dedicated Vector(VectorGraphics) variant. Derive Serialize and Deserialize on all structural asset layouts.
  3. Create an AssetManifest struct containing a std::collections::HashMap<String, Asset> that maps unique string lookup names (GUIDs, like "player_ship") to their target properties.
  4. Implement the following concrete API interfaces on your AssetManifest context block: 
    impl AssetManifest {

    pub fn register_svg(&mut self, guid: &str, file_path: &str, w: f32, h: f32) -> std::io::Result<()>;
    pub fn save_to_json(&self, path: &str) -> std::io::Result<()>;
    pub fn load_from_json(path: &str) -> std::io::Result<Self>;

Description

In this exercise, you will upgrade your asset management layer. You will write a tool that imports your text-based asset manifest from Exercise 06 and converts it directly into a highly efficient binary blob structure using the zero-overhead bincode format.

Exercise 08: Decoupled Simulation & Fixed Timestep Loops
To do after: Ex 07
Turn-in directory: ex08/
Files to turn in: Cargo.toml, src/main.rs
Allowed external crates: None (Standard library only)

Description

To prevent physics-simulation divergence during variable-speed frame rendering, this module introduces the Fixed Timestep Accumulator model. By decoupling the simulation rate from the rendering rate, we ensure deterministic behavior regardless of hardware performance.

Sub-Exercise 8.1: The Precision Timer

Implement a loop using std::time::Instant to measure the delta time (Δt) between iterations. Print the current elapsed Δt in milliseconds. Verify your system is reporting time intervals consistently before moving to logic integration.

Sub-Exercise 8.2: The Accumulator Reservoir

Define an accumulator: f32 variable. Add the measured Δt from 8.1 into this reservoir every loop. Trigger a "Physics Tick" log only when the accumulator reaches or exceeds 20ms, then subtract exactly 20ms from the accumulator.

Sub-Exercise 8.3: The Deterministic Physics Step

Abstract your physics logic into a function fn update_physics(dt: f32). Update your while loop to execute this function exactly once for every 20ms slice consumed from the accumulator. This ensures the simulation progresses in discrete, predictable units of time.

Sub-Exercise 8.4: The Lag-Stress Test

Simulate processing spikes: introduce a counter that uses std::thread::sleep to alternate stall lengths between 10ms and 55ms. Verify that during the 55ms stall, the engine correctly processes multiple physics ticks (3 ticks: 60ms consumed) in a single loop cycle to "catch up" the simulation state.

Requirements

  1. Target fixed timestep constant (Δtfixed): 20ms (50 ticks/sec).
  2. Print [PHYSICS] Stepping 2D Physics Matrix: 20ms per tick.
  3. Print [RENDER] Rasterizing active SVG shapes to screen per loop iteration.
  4. Terminate program cleanly after exactly 10 render loops.
Exercise 09: Cache-Aligned 2D Vector ECS Architecture
To do after: Ex 08
Turn-in directory: ex09/
Files to turn in: Cargo.toml, src/main.rs
Allowed external crates: None (Standard library only)

Description

Object-oriented layouts bundle structural behaviors together (e.g., an actor class containing names, matrix objects, vector drawing XML text strings, and processing states). This design introduces massive runtime performance bottlenecks because it scatters components across unaligned memory blocks on the heap. When an engine runs loops to update object positions, it is forced to load irrelevant graphic strings into the CPU cache line, wasting memory bandwidth.

An Entity Component System (ECS) optimizes this layout by splitting data properties into parallel, flat, contiguous arrays. This architecture ensures that spatial physics systems iterate sequentially through closely packed position numbers, maximizing CPU L1/L2 cache locality.

Requirements

  1. Define a unique identifier type alias named Entity mapping directly to usize.
  2. Define three pure data component structures:
    • Transform2D: Struct containing spatial coordinates: x: f32, y: f32, scale: f32.
    • Motion2D: Struct containing movement vectors: vx: f32, vy: f32.
    • SvgRender: Struct containing a reference identifier keying back to the vector graphics asset bundle: asset_guid: String.
  3. Construct a World simulation struct designed to keep component segments packed closely together in flat, contiguous vectors aligned by index lookup: 
    pub struct World {
    transforms: Vec<Option<Transform2D>>,
    motions: Vec<Option<Motion2D>>,
    renders: Vec<Option<SvgRender>>,
    next_id: usize,
}
  4. Implement the following methods on your central World structure:
    • pub fn new() -> Self;
    • pub fn spawn_actor(&mut self) -> Entity;
    • pub fn attach_transform(&mut self, entity: Entity, t: Transform2D);
    • pub fn attach_motion(&mut self, entity: Entity, m: Motion2D);
    • pub fn attach_render(&mut self, entity: Entity, r: SvgRender);
  5. Implement an isolated system pipeline function: pub fn step_kinematics(world: &mut World). This function must iterate linearly through the components. For every entity slot index that holds active data for both Transform2D and Motion2D, update its positions:
    transform.x += motion.vx;
    transform.y += motion.vy;

Exercise 10: The Engine Virtual File System (VFS)
To do after: Ex 09
Turn-in directory: ex10/
Files to turn in: Cargo.toml, src/lib.rs, src/main.rs
Allowed external crates: None (Standard library only)

Description

Hardcoding platform-specific absolute file paths (e.g., C:\Users\Game\assets\player.svg or /home/user/game/assets/player.svg) directly into system load calls limits cross-platform deployment. To ensure smooth execution across all targets, game engines decouple physical paths using a logical Virtual File System (VFS) protocol.

A VFS registers a unified high-level path syntax namespace (e.g., "game://sprites/hero.svg") and translates it dynamically into valid platform-relative directory paths at runtime depending on where the application execution target is rooted.

Requirements

  1. Create an EngineVFS struct that tracks the base folder workspace root path using a std::path::PathBuf container.
  2. Implement the initialization constructor: pub fn new(base_path: &str) -> Self;.
  3. Implement the routing resolution methodology: pub fn resolve_vfs_uri(&self, uri: &str) -> Result<std::path::PathBuf, &'static str>;.
  4. Your path translation function must parse asset URI formatting protocols:
    • "game://assets/ui.svg" translates relative to: [base_path]/game/assets/ui.svg.
    • "engine://core/fallback.svg" translates relative to: [base_path]/engine/core/fallback.svg.
  5. Security Boundary: If a path string contains directory traversal escape markers (e.g., testing for "../" sequences intended to break out of the engine workspace root directory), your allocator must intercept it immediately and return an Err("VFS Traversal Security Infraction"). Failure to prevent traversal manipulation is a strict **KO**.
Exercise 11: Polymorphic Scene State Node Management
To do after: Ex 10
Turn-in directory: ex11/
Files to turn in: Cargo.toml, src/main.rs
Allowed external crates: None (Standard library only)

Description

A production-ready game engine must organize separate states of execution cleanly (e.g., clearing background menus when loading levels, or caching background worlds when overlaying inventory screens). Loading every single asset registry, tracking hash, and physics simulation entity array into a single monolithic loop is impossible to maintain.

In this exercise, you will implement a modular, type-safe Polymorphic Scene Stack Manager that isolates runtime execution loops into clean, decoupled context layers using Rust trait objects.

Requirements

  1. Define a Scene trait containing three operational lifecycle state hooks: 
    pub trait Scene {
    fn on_scene_enter(&mut self);
    fn on_scene_tick(&mut self) -> Option<SceneTransition>
    fn on_scene_exit(&mut self);
}
  2. Define an adjustment routing enum named SceneTransition containing two distinct stack mutations:
    • Push(Box<dyn Scene>): Suspends execution of the current scene and stacks a new context over it.
    • Pop: Unloads and discards the active top scene context, returning execution back to the underlying layer.
  3. Create a SceneStackController struct that tracks active execution contexts sequentially using a vector array stack layout: active_layers: Vec<Box<dyn Scene>>.
  4. Implement the following methods on your controller structure:
    • pub fn push_context(&mut self, mut scene: Box<dyn Scene>): Automatically executes the on_scene_enter() method of the incoming scene before storing it onto the stack array.
    • pub fn process_tick(&mut self) -> bool: Runs the on_scene_tick() callback of the top scene context. If a transition is returned, execute the state mutation and run the appropriate cleanup hook (on_scene_exit()). Returns false if the stack becomes completely empty, signaling the engine to close.
Exercise 12: Desktop Windowing & Integrated Engine Frame Runtime

Description

To complete your desktop engine core, you must interface directly with the operating system's window manager server. Modern desktop environments run on an Event-Driven Message Inversion Loop. The operating system handles hardware interactions (resizing, canvas draw triggers, close signals) and routes them into an application message queue.

In this final integration exercise, you will marry all systems together. You will build an active window loop via winit and embed your **Fixed Timestep Accumulator (Ex 08)** and your **Polymorphic Scene Controller (Ex 11)** completely inside the OS lifecycle handler layout.

Requirements

  1. Add the low-level window abstraction utility to your dependencies: 
    [dependencies]
winit = "0.29"
  2. Create an engine container named VectorEngineRuntime that holds:
    • window_surface: Option<winit::window::Window>
    • scene_controller: SceneStackController (From Ex 11)
    • last_frame_time: std::time::Instant
    • accumulator: f32 (The tracking timeline reservoir from Ex 08, tracked in seconds or milliseconds)
  3. Implement the winit::application::ApplicationHandler trait on your VectorEngineRuntime container. You must integrate your subsystems across these three hooks:
    • resumed: Instantiate your window here using Window::default_attributes().with_title("2D SVG Vector Engine").
    • window_event: Handle WindowEvent::CloseRequested to shut down cleanly via event_loop.exit().
    • about_to_wait: The Engine Loop Heartbeat. Calculate the delta time since `last_frame_time`. Add it to your `accumulator`. While `accumulator` is greater than or equal to your fixed timestep (20ms), execute scene_controller.process_tick(). If the scene controller signals the stack is empty, invoke event_loop.exit(). Finally, request a frame draw pass via window.request_redraw().

Expected Engine Entry Execution Architecture

use winit::application::ApplicationHandler;
use winit::event::WindowEvent;
use winit::event_loop::{ActiveEventLoop, EventLoop, ControlFlow};
use winit::window::{Window, WindowId};
use std::time::{Instant, Duration};

// Mock structures placeholder matching your Ex 11 implementation requirements
pub struct SceneStackController {}
impl SceneStackController {
    pub fn process_tick(&mut self) -> bool {
        println!("[PHYSICS SYSTEM] Stepping 2D Matrix via Active Scene: 20ms");
        true // Returns false if engine should terminate
    }
}

struct VectorEngineRuntime {
    window_surface: Option<Window>,
    scene_controller: SceneStackController,
    last_frame_time: Instant,
    accumulator: f32,
}

impl ApplicationHandler for VectorEngineRuntime {
    fn resumed(&mut self, event_loop: &ActiveEventLoop) {
        if self.window_surface.is_none() {
            let attribs = Window::default_attributes()
                .with_title("2D SVG Vector Forge Engine")
                .with_inner_size(winit::dpi::LogicalSize::new(1024.0, 768.0));
            
            let win = event_loop.create_window(attribs).unwrap();
            println!("[ENGINE] Host OS Desktop Canvas allocated successfully.");
            self.window_surface = Some(win);
            self.last_frame_time = Instant::now();
        }
    }

    fn window_event(&mut self, event_loop: &ActiveEventLoop, _id: WindowId, event: WindowEvent) {
        match event {
            WindowEvent::CloseRequested => {
                println!("[TEARDOWN] Tearing down engine runtime vectors...");
                event_loop.exit();
            }
            WindowEvent::RedrawRequested => {
                if let Some(_window) = &self.window_surface {
                    println!("[RENDER PATH] Rasterizing active SVG shapes to screen");
                }
            }
            _ => ()
        }
    }

    fn about_to_wait(&mut self, event_loop: &ActiveEventLoop) {
        if let Some(window) = &self.window_surface {
            let current_time = Instant::now();
            let delta_time = current_time.duration_since(self.last_frame_time).as_secs_f32();
            self.last_frame_time = current_time;

            // Step 1: Accumulate execution time pools (Ex 08 pattern)
            self.accumulator += delta_time;

            // Step 2: Flush ticks at fixed structural durations (20ms)
            const FIXED_TIMESTEP: f32 = 0.020; // 20 milliseconds
            while self.accumulator >= FIXED_TIMESTEP {
                if !self.scene_controller.process_tick() {
                    event_loop.exit();
                    return;
                }
                self.accumulator -= FIXED_TIMESTEP;
            }

            // Step 3: Trigger a variable rendering refresh frame pass
            window.request_redraw();
        }
    }
}

fn main() {
    println!("[BOOT] Bootstrapping structural engine runtime systems...");
    let loop_event = EventLoop::new().unwrap();
    loop_event.set_control_flow(ControlFlow::Poll);

    let mut runtime = VectorEngineRuntime { 
        window_surface: None,
        scene_controller: SceneStackController {},
        last_frame_time: Instant::now(),
        accumulator: 0.0,
    };
    loop_event.run_app(&mut runtime).unwrap();
}
