Module GE02-B: Gentle Intro to Vector Windowing
Pacing & Curriculum Note:

Transitioning to desktop application design can feel overwhelming if we try to learn window event loops, GPU rendering pipelines, vector math, and DPI scaling all at once.

This module uses a smooth step-by-step progression. Each exercise introduces only one new concept:

  • Exercise 01: Window Lifecycle (`winit`)
  • Exercise 02: Modern Vector Scene Base (`vello` + background clear)
  • Exercise 03: Drawing Basic Shapes (`kurbo` vector primitives)
  • Exercise 04: Vector Translation & Motion (Moving shapes in 2D vector space)
  • Exercise 05: DPI & Resolution Independence (Scaling viewports smoothly)

Theoretical Overview: What is a Vector Scene?

Instead of modifying individual pixels in a grid ($I = Y \times W + X$), modern user interfaces construct a Scene Graph made of shapes (rectangles, circles, curves).

When you tell a vector engine to draw a shape, you give it a mathematical description (e.g., "draw a circle at center (100, 100) with radius 50"). The engine then draws this shape smoothly onto the display at whatever resolution the screen supports.

Concretely, in this module the shapes live in a vello::Scene — an object you can build and rebuild freely on the CPU with no GPU involved at all. GPU work only enters the picture once, at the very last step of each frame, when you hand that Scene to a vello::Renderer to actually turn it into pixels. Exercise 02 walks through exactly what has to exist before that handoff can happen.

Exercise 01: Creating the Application Window
Step 1: The Event Loop
Turn-in directory: ex01/
Files to turn in: Cargo.toml, src/main.rs
Allowed external crates: winit (v0.29.x or v0.30.x)

Goal

Open a blank desktop window titled "Vector Shell" and handle the close button properly.

Why a struct and a trait, not just a function?

A desktop window isn't something you draw once and forget — the OS keeps sending it messages ("resize me," "you were just minimized," "the user clicked close") for as long as it exists, in an order you don't control. Rust's answer to "run some code every time an unpredictable event arrives" is: put your data in a struct, and implement a trait whose methods the OS calls back into. That's all ApplicationHandler is — a contract that says "call resumed once you have a window to give me, then call window_event every time something happens to it." You never call these methods yourself; winit calls them for you from inside run_app.

Two methods, two jobs: resumed() fires once (right at startup, and again if the OS ever tears the window down and hands it back — mainly relevant on mobile) — this is where you create the window. window_event() fires repeatedly, once per OS message — this is where you react to things that already happened.

Step-by-Step Instructions

  • Step 1.1: Run cargo init ex01, then add winit = "0.30" under [dependencies] in Cargo.toml (or run cargo add winit@0.30 instead of hand-editing the file).
  • Step 1.2: Define a struct named AppShell with one field: window: Option<Arc<Window>>. It starts as None because the moment your program starts, the OS hasn't handed you a window yet — that only happens inside resumed(). Add #[derive(Default)] above the struct so you can construct it as AppShell::default() without writing a constructor by hand.
  • Step 1.3: Implement ApplicationHandler for AppShell (copy the method signatures from the skeleton below exactly — winit won't call your methods if a signature doesn't match the trait). Inside resumed(): check if self.window.is_none() first, since this method can run more than once and you don't want to accidentally spawn a second window; then build a WindowAttributes with .with_title("Vector Shell"), pass it to event_loop.create_window(...), wrap the result in Arc::new(...), and store it in self.window.
  • Step 1.4: Inside window_event(), match on the incoming event. When it's WindowEvent::CloseRequested (fired when the user clicks the window's close button), call event_loop.exit() — skip this and clicking close does nothing, and you'll have to kill the process from the terminal instead.
  • Step 1.5: In main(), build the loop with EventLoop::new().unwrap(), construct AppShell::default(), and hand control to winit with event_loop.run_app(&mut app).unwrap(). This call blocks until exit() is called — from here on, everything your app does happens inside the two methods above, not in main.

Starter Code Skeleton

use std::sync::Arc;
use winit::application::ApplicationHandler;
use winit::event::WindowEvent;
use winit::event_loop::{ActiveEventLoop, EventLoop};
use winit::window::{Window, WindowId};

#[derive(Default)]
struct AppShell {
    window: Option<Arc<Window>>,
}

impl ApplicationHandler for AppShell {
    fn resumed(&mut self, event_loop: &ActiveEventLoop) {
        if self.window.is_none() {
            let attr = Window::default_attributes().with_title("Vector Shell");
            let win = Arc::new(event_loop.create_window(attr).unwrap());
            self.window = Some(win);
        }
    }

    fn window_event(&mut self, event_loop: &ActiveEventLoop, _id: WindowId, event: WindowEvent) {
        if let WindowEvent::CloseRequested = event {
            event_loop.exit();
        }
    }
}

fn main() {
    let event_loop = EventLoop::new().unwrap();
    let mut app = AppShell::default();
    event_loop.run_app(&mut app).unwrap();
}
Exercise 02: Presenting a Vector Background Color
Step 2: The Vector Scene
Turn-in directory: ex02/
Files to turn in: Cargo.toml, src/main.rs
Allowed external crates: winit, vello, wgpu, pollster

Goal

Connect a vector renderer (vello) to your window and clear the background with a soft vector color: Deep Salmon Pink (Color::from_rgb8(255, 140, 148)).

What "initializing the vector context" actually means

This is the step most beginners get stuck on, because "connect a renderer to your window" hides four separate objects you need to create, in order, before you can draw a single pixel. Here's what each one is and why it exists:

  • wgpu::Instance — your entry point into the GPU drivers on the machine. You create exactly one of these, usually with wgpu::Instance::default().
  • wgpu::Surface — the thing wgpu draws into that the OS displays on screen. You get one from instance.create_surface(window.clone()) — this is why your window needs to be wrapped in an Arc: the surface borrows it for as long as the surface exists.
  • wgpu::Device and wgpu::Queue — your actual handle to the GPU. The Device creates GPU resources (textures, buffers); the Queue is where you submit rendering work to actually run. You get both together, asynchronously, via instance.request_adapter(...) then adapter.request_device(...).
  • vello::Renderer — built once you have a Device, this is the object that knows how to turn a Scene (your list of shapes) into pixels on a Surface.

One wrinkle: steps 2 and 3 above are async functions, but resumed() is not an async method — winit calls it synchronously. The fix is pollster::block_on(...), which is why pollster is in your dependency list: it runs an async block to completion right there, blocking the current thread instead of yielding control.

Step-by-Step Instructions

  • Step 2.1: Add vello = "0.5", wgpu = "27.0", and pollster = "0.3" to Cargo.toml (or cargo add vello wgpu pollster and let Cargo pick current compatible versions).
  • Step 2.2: Create a state struct VectorCanvas holding: window: Option<Arc<Window>>, surface: Option<wgpu::Surface<'static>>, device: Option<wgpu::Device>, queue: Option<wgpu::Queue>, renderer: Option<vello::Renderer>, and scene: vello::Scene (this last one doesn't need to be an Option — Scene::new() gives you an empty scene immediately, no GPU needed).
  • Step 2.3: Inside resumed(), after creating the window as in Exercise 01: build the four objects listed above, in that exact order (each one is built from the previous one), wrapping the async calls in pollster::block_on. Store all five results in self.
  • Step 2.4: Configure the surface once, right after creating it, with surface.configure(&device, &surface_config) — a wgpu::SurfaceConfiguration tells wgpu the pixel format and size to render at; without this call, get_current_texture() later will panic.
  • Step 2.5: In window_event(), match on WindowEvent::RedrawRequested. Inside it: call self.scene.reset() (clears last frame's shapes so they don't pile up), get the next frame with surface.get_current_texture(), then call renderer.render_to_surface(device, queue, &self.scene, &surface_texture, &RenderParams { base_color: Color::from_rgb8(255, 140, 148), width, height, antialiasing_method: vello::AaConfig::Msaa16 }), and finally surface_texture.present() to actually show the frame on screen.
  • Step 2.6: Nothing triggers RedrawRequested on its own yet — call window.request_redraw() once at the end of resumed() so you see your salmon-pink window at all.

Syntactic Architecture & Signatures

use vello::{peniko::Color, AaConfig, RenderParams, Renderer, RendererOptions, Scene};

struct VectorCanvas {
    window: Option<Arc<winit::window::Window>>,
    surface: Option<wgpu::Surface<'static>>,
    surface_config: Option<wgpu::SurfaceConfiguration>,
    device: Option<wgpu::Device>,
    queue: Option<wgpu::Queue>,
    renderer: Option<Renderer>,
    scene: Scene,
}

// Inside resumed(), after self.window is set (see Exercise 01):
let instance = wgpu::Instance::default();
let surface = instance.create_surface(window.clone()).unwrap();
let adapter = pollster::block_on(instance.request_adapter(
    &wgpu::RequestAdapterOptions {
        compatible_surface: Some(&surface),
        ..Default::default()
    },
)).unwrap();
let (device, queue) = pollster::block_on(
    adapter.request_device(&wgpu::DeviceDescriptor::default())
).unwrap();

let size = window.inner_size();
let surface_config = surface
    .get_default_config(&adapter, size.width.max(1), size.height.max(1))
    .unwrap();
surface.configure(&device, &surface_config);

let renderer = Renderer::new(&device, RendererOptions::default()).unwrap();

// In WindowEvent::RedrawRequested:
self.scene.reset();
let surface_texture = self.surface.as_ref().unwrap().get_current_texture().unwrap();
self.renderer.as_mut().unwrap().render_to_surface(
    self.device.as_ref().unwrap(),
    self.queue.as_ref().unwrap(),
    &self.scene,
    &surface_texture,
    &RenderParams {
        base_color: Color::from_rgb8(255, 140, 148), // Deep Salmon Pink
        width: self.surface_config.as_ref().unwrap().width,
        height: self.surface_config.as_ref().unwrap().height,
        antialiasing_method: AaConfig::Msaa16,
    },
).unwrap();
surface_texture.present();
Exercise 03: Adding Your First Vector Shape
Step 3: Vector Geometry
Turn-in directory: ex03/
Files to turn in: Cargo.toml, src/main.rs
Allowed external crates: winit, vello, kurbo, wgpu, pollster

Goal

Draw a solid **Gold Rounded Rectangle** (100x100px, corner radius 16px) on top of your background color using 2D vector geometry primitives.

Step-by-Step Instructions

  • Step 3.1: Add kurbo = "0.11" (the standard 2D vector geometry library — it defines shapes and math, but knows nothing about GPUs or rendering) to Cargo.toml.
  • Step 3.2: Define a shape primitive using kurbo::RoundedRect::new(x0, y0, x1, y1, radius). Note this takes two corners, not a corner plus a width/height — for a rectangle at $X=50, Y=50$ that's $100 \times 100$, the second corner is $(50+100, 50+100) = (150, 150)$, which is why the code below reads RoundedRect::new(50.0, 50.0, 150.0, 150.0, 16.0).
  • Step 3.3: Call scene.fill(...) to add the shape to your scene graph. It takes five arguments, in order — worth understanding each rather than treating them as boilerplate:
    • Fill::NonZero — the fill rule, which only matters for self-intersecting or nested shapes (it decides which regions count as "inside"). For a plain rectangle it's irrelevant; NonZero is simply the conventional default.
    • Affine::IDENTITY — a 2D transform matrix applied to the shape before drawing. IDENTITY means "no transform" — draw the shape exactly at the coordinates you gave it. You'll replace this with a real transform in Exercise 04 to move the shape without redefining its geometry.
    • Color::from_rgb8(255, 215, 0) — the fill color (Gold).
    • None — an optional gradient Brush transform; None means "use the solid color as-is, no gradient."
    • &rect — the shape itself, borrowed since scene.fill only needs to read its geometry.
    let rect = kurbo::RoundedRect::new(50.0, 50.0, 150.0, 150.0, 16.0);
scene.fill(
    vello::peniko::Fill::NonZero,
    kurbo::Affine::IDENTITY,
    vello::peniko::Color::from_rgb8(255, 215, 0), // Gold
    None,
    &rect,
);
  • Step 3.4: Call scene.fill(...) before renderer.render_to_surface(...) in your RedrawRequested handler from Exercise 02 (after scene.reset(), since reset() wipes anything drawn on a previous frame). Render the frame to see your sharp, anti-aliased vector shape.
Exercise 04: Moving Shapes with Vector Translation
Step 4: Vector Coordinates & Motion
Turn-in directory: ex04/
Files to turn in: Cargo.toml, src/main.rs
Allowed external crates: winit, vello, kurbo, wgpu, pollster

Goal

Make your gold rectangle interactive! Store position coordinates $(X, Y)$ in your state and move the vector shape smoothly when pressing the arrow keys.

Step-by-Step Instructions

  • Step 4.1: Add pos_x: f64 and pos_y: f64 to your application state, initialized to (50.0, 50.0).
  • Step 4.2: Catch WindowEvent::KeyboardInput { event, .. } inside window_event(). This is the fiddliest match in the exercise, since the key you actually want is nested three levels deep: the outer event holds a KeyEvent, which holds a logical_key: Key, which for a named key (arrows, Enter, Escape, etc. — as opposed to a letter or digit) is the variant Key::Named(NamedKey::ArrowUp) (and so on for ArrowDown/ArrowLeft/ArrowRight). You also usually want to check event.state == ElementState::Pressed, or your rectangle will move again on key release too. Putting it together: 
    use winit::event::{ElementState, KeyEvent};
use winit::keyboard::{Key, NamedKey};

WindowEvent::KeyboardInput {
    event: KeyEvent { logical_key: Key::Named(key), state: ElementState::Pressed, .. },
    ..
} => match key {
    NamedKey::ArrowUp    => self.pos_y -= 10.0,
    NamedKey::ArrowDown  => self.pos_y += 10.0,
    NamedKey::ArrowLeft  => self.pos_x -= 10.0,
    NamedKey::ArrowRight => self.pos_x += 10.0,
    _ => {}
},
    (Screen Y increases downward, which is why ArrowUp subtracts.)
  • Step 4.3: Instead of recreating the rectangle math, apply a translation offset using kurbo::Affine::translate((self.pos_x, self.pos_y)) as the second argument to scene.fill(...), in place of the Affine::IDENTITY from Exercise 03. Also change your RoundedRect definition to start at the origin — RoundedRect::new(0.0, 0.0, 100.0, 100.0, 16.0) — so the translation is the only thing positioning it; otherwise you'd be adding pos_x/pos_y on top of the rectangle's own (50, 50) offset from before.
  • Step 4.4: Call window.request_redraw() at the end of the key-handling branch. Without it, you've updated self.pos_x/self.pos_y in memory, but RedrawRequested never fires again on its own, so the screen won't update until some other event happens to trigger a redraw.

Syntactic Architecture & Signatures

use kurbo::Affine;

// In your scene drawing logic:
let shape = kurbo::RoundedRect::new(0.0, 0.0, 100.0, 100.0, 16.0);
let transform = Affine::translate((self.pos_x, self.pos_y));

scene.fill(Fill::NonZero, transform, Color::from_rgb8(255, 215, 0), None, &shape);
Exercise 05: Resolution Independence & Viewport Scaling
Step 5: DPI & Dynamic Resizing
Turn-in directory: ex05/
Files to turn in: Cargo.toml, src/main.rs
Allowed external crates: winit, vello, kurbo, wgpu, pollster

Goal

Handle window resizing and high-DPI (Retina/4K) displays so your vector shapes stay crystal clear without becoming tiny or pixelated.

What "scale factor" actually is, concretely

A "4K" or "Retina" monitor packs more physical pixels into the same physical inch of screen than an older monitor did. If your app draws a "100×100 pixel" rectangle by placing exactly 100 physical pixels on screen, that rectangle will be physically tiny on a high-density display — roughly a postage stamp instead of a comfortable button. The OS's fix is to report a scale factor alongside window events: a plain monitor reports 1.0, a typical Retina display reports 2.0, and you'll see values like 1.5 or 1.25 on some Windows/Linux setups. This number tells you "for every one logical pixel the user expects, actually draw this many physical pixels."

Two different sizes flow through winit, and mixing them up is the most common bug in this exercise: logical size (what your UI is conceptually laid out in — a 100×100 rectangle is still "100×100" regardless of monitor) and physical size (actual device pixels — logical × scale_factor). Your GPU surface must always be configured in physical pixels (that's what WindowEvent::Resized gives you), but the shapes in your Scene are defined in logical coordinates — which is exactly what the scale transform in Step 5.4 bridges.

Step-by-Step Instructions

  • Step 5.1: Store a scale_factor: f64 in your state struct, initialized to 1.0 as a placeholder — you'll overwrite it with the real value the first time you get a chance (see Step 5.3), so 1.0 just avoids needing an Option.
  • Step 5.2: Handle WindowEvent::Resized(physical_size): this fires whenever the window's pixel dimensions change (the user dragged an edge, maximized it, etc.), and physical_size is already in physical pixels. Update self.surface_config.width and .height to the new values (guard against 0 — see the code below, since a minimized window reports size 0 and reconfiguring to zero size will panic), then call surface.configure(&device, &surface_config) again so the GPU knows the new size.
  • Step 5.3: Handle WindowEvent::ScaleFactorChanged { scale_factor, .. }: this fires when the window moves to a monitor with a different pixel density (common with multi-monitor setups mixing a laptop screen and an external display), or once early on to report the initial value. Store the new scale_factor in self.scale_factor and call window.request_redraw(), since your shapes need to be redrawn at the new scale.
  • Step 5.4: When filling your scene, replace the plain Affine::translate(...) from Exercise 04 with Affine::scale(self.scale_factor) * Affine::translate((self.pos_x, self.pos_y)) — matrix multiplication order matters here: this scales after translating, so your logical coordinates ($100 \times 100$ at position (pos_x, pos_y)) get converted to physical pixels as the very last step, right before rendering, while everything else in your code keeps working in simple logical units.

Syntactic Architecture & Signatures

impl VectorCanvas {
    fn handle_resize(&mut self, new_size: winit::dpi::PhysicalSize<u32>) {
        if new_size.width > 0 && new_size.height > 0 {
            self.surface_config.width = new_size.width;
            self.surface_config.height = new_size.height;
            self.surface.as_ref().unwrap().configure(
                self.device.as_ref().unwrap(), 
                &self.surface_config
            );
        }
    }
}

// In window_event():
WindowEvent::Resized(new_size) => self.handle_resize(new_size),

WindowEvent::ScaleFactorChanged { scale_factor, .. } => {
    self.scale_factor = scale_factor;
    if let Some(window) = &self.window {
        window.request_redraw();
    }
}

// When filling the scene each frame:
let transform = Affine::scale(self.scale_factor)
    * Affine::translate((self.pos_x, self.pos_y));
scene.fill(Fill::NonZero, transform, Color::from_rgb8(255, 215, 0), None, &shape);
